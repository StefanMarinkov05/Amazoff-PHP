# SEC-014 — seven storefront Livewire properties crash at hydration on an oversized `$set`

Part of the [security-testing index](../security-testing.md). See
[method-and-summary.md](method-and-summary.md) for how this pass was run.

### SEC-014 — Strictly-typed numeric Livewire properties throw an uncaught `TypeError` before component code runs

**Severity:** Low (unhandled crash / local information disclosure under
`APP_DEBUG=true`; no data corruption, no IDOR) · **Type:** Improper input
handling leading to denial of a single request (adjacent to OWASP A05
Security Misconfiguration — an unhandled exception path) · **Status:**
**Fixed** 2026-09-13 — confirmed by live exploitation, then closed for all
seven properties

**Finding.** `docs/how-to/test-for-input-crashes.md` had already documented
four instances of one mechanism: Livewire 3.8.3's
`HandleComponents::setComponentPropertyAwareOfTypes()` assigns a client-sent
value straight onto a public typed property during hydration, *before* any
of the component's own code runs, and re-throws the `TypeError` if the value
does not fit the declared type. The four fixed instances (`quantity`,
`variationId`, `brandId`, `categoryId`) were all `#[Url]`/route-param driven.
A grep for every `public int`/`?int`/`float`/`?float` property **not**
already `#[Locked]` across every storefront Livewire component found seven
more, reachable the same way but never bound to a URL or route parameter —
plain `$set()` over the `/livewire/update` endpoint reaches them just as
directly:

| Property | Type before fix | Client-set how |
|---|---|---|
| `OrderConfirmation::$orderId` | `int`, not `#[Locked]` | direct `$set` |
| `ProductDetails::$productId` | `?int`, not `#[Locked]` | direct `$set` |
| `ProductDetails::$imageIndex` | `int`, not `#[Locked]` | direct `$set` |
| `ManageAddresses::$editingId` | `?int`, not `#[Locked]` | direct `$set` |
| `ProductDetails::$reviewRating` | `int` | `wire:click="$set('reviewRating', N)"` — legitimately client-set |
| `CheckoutPage::$carrier_id` | `?int` | `wire:model.live` on the carrier radio group |
| `CheckoutPage::$selected_address_id` | `?int` | `wire:model.live` on the saved-address picker |

Every one of the four `#[Locked]`-eligible properties (`orderId`,
`productId`, `imageIndex`, `editingId`) is set only by server-side code
(`mount()`, or a method like `startEditing()`/`setImage()`) and never
targeted by a blade `$set()` or `wire:model` — confirmed by grepping the
corresponding blade views before locking each one, since `#[Locked]` throws
`CannotUpdateLockedPropertyException` on *any* client write and would break
a feature that legitimately needs one. The other three
(`reviewRating`, `carrier_id`, `selected_address_id`) are genuinely
client-driven and cannot be locked; they were widened to `mixed` instead,
matching the fix `ProductDetails::$quantity` already used for the same
incident class, with a normalising hook (`updated()`/
`updatedSelectedAddressId()`) or the existing submit-time validation rule
still guarding what is actually persisted.

**Reason.** `#[Url]`/route-param hydration was the previously-known trigger,
but the underlying mechanism is Livewire's property hydration in general —
it runs on *every* `$set()` and every `wire:model` update, regardless of
whether the property is also bound to the URL. A strictly-typed `int`/`float`
property is exposed to this the moment it is `public`, independent of what
the rendered form does with it. `test-for-input-crashes.md` had predicted
exactly this ("the fourth instance → grep the whole codebase in one pass"),
naming the next sweep as extending past `#[Url]` properties to every typed
numeric property; this pass is that sweep.

**Reproduction (confirmed live for each, via `Livewire::test()->set()`
against the real component — not assumed from the type alone).** A 34-digit
numeric string (`'99999999999999999999999999999999'`, past `PHP_INT_MAX`,
decodes to a `float` before Livewire's hydration assigns it) against each
property threw an uncaught
`TypeError: Cannot assign string to property ...::$<property> of type <type>`,
before any of `mount()`/the target method ran:

```
$set('orderId', '99999999999999999999999999999999')            → TypeError
$set('productId', '99999999999999999999999999999999')           → TypeError
$set('imageIndex', '99999999999999999999999999999999')          → TypeError
$set('editingId', '99999999999999999999999999999999')           → TypeError
$set('reviewRating', '99999999999999999999999999999999')        → TypeError
$set('carrier_id', '99999999999999999999999999999999')          → TypeError
$set('selected_address_id', '99999999999999999999999999999999') → TypeError
```

Under local `APP_DEBUG=true` this renders a full Ignition trace (file
paths, the framework/PHP version, the dependency-resolution stack) to
whichever visitor sent the request — including an anonymous one, since none
of these properties sit behind an authorization check that runs before
hydration. With debug off the same input still 500s; the difference is only
whether the response body leaks anything.

None of the seven is an IDOR or an authorization bypass on its own:

- `orderId`, `productId`, `editingId` are all re-scoped through an
  entitlement check on every render (`authorizedOrder()`,
  `Product::findOrFail()` against `is_available`,
  `$this->user()->addresses()->findOrFail()`), so a client-set id that
  survives hydration still cannot read another customer's data — the bug is
  purely that hydration crashes before that check is ever reached.
- `imageIndex` only selects among a product's own already-public images.
- `reviewRating`, `carrier_id`, `selected_address_id` all still go through
  their own submit-time validation (`integer|min:1|max:5`,
  `integer|exists:carriers,id,is_active,true`, and an owner-scoped
  `addresses()->find()` respectively) — the crash pre-empts that validation
  rather than bypassing it.

**Fix.** Two shapes, chosen per property by whether the UI itself legitimately
sets it:

1. **`#[Locked]`** for the four server-managed ids (`orderId`, `productId`,
   `imageIndex`, `editingId`). Livewire refuses any client write to a
   `#[Locked]` property with `CannotUpdateLockedPropertyException` rather
   than attempting the type coercion that crashed — the safest fix where
   available, since it removes the client's ability to write the property
   at all rather than only widening what it can write.
2. **`mixed`, with the existing normalisation left in place** for the three
   properties a `wire:model`/`$set` binding actually drives
   (`reviewRating`, `carrier_id`, `selected_address_id`) — the same shape
   `ProductDetails::$quantity` already used for this incident class.
   `carrier_id` gained a normalising branch in `CheckoutPage::updated()`
   (mirroring `ProductDetails::mount()`'s own numeric-or-null coercion for
   `$variationId`) since nothing previously converted its raw client value
   back to a real id or `null`; `selected_address_id` already had that
   normalisation in `updatedSelectedAddressId()`, so widening the property
   type alone was sufficient there; `reviewRating` needed no new
   normalisation, since `submitReview()`'s `integer|min:1|max:5` rule
   already guards what is persisted regardless of what hydration assigns.

Each fix has a permanent regression test verified **red** before the fix
(reverting the type/lock reproduces the same `TypeError`, or — for the
locked properties — reproduces a bare `set()` succeeding instead of
throwing `CannotUpdateLockedPropertyException`) and green after:
`tests/Feature/Livewire/OrderConfirmationOrderIdTest.php`,
`tests/Feature/Livewire/ProductDetailsLockedIdsTest.php`,
`tests/Feature/Livewire/ManageAddressesEditingIdTest.php`,
`tests/Feature/Livewire/CheckoutPageHydrationTest.php`, and
`tests/Feature/Livewire/ProductDetailsReviewRatingHydrationTest.php`.

**Logic for future pentests.** The trigger is not "a property bound to
`#[Url]`" — it is "a public property with a strict numeric type that the
client can reach via `$set()` or `wire:model`, however indirectly." Every
`wire:model`-bound field on a number input has no server-side ceiling from
the input's own `min`/`max` attributes, and every public property is
reachable via `$set()` over `/livewire/update` regardless of whether any
rendered control targets it. Grep target for the next component:
`public (?:\??)(?:int|float)\b` properties without `#[Locked]`, cross-checked
against the component's own blade view for whether a `$set()`/`wire:model`
binding legitimately reaches them (→ widen to `mixed` and keep/add
normalisation) or nothing does (→ `#[Locked]`). This sweep was bounded to
storefront Livewire components per `test-for-input-crashes.md`'s own scope;
Filament admin-panel components were not swept and are a candidate for the
same grep.
