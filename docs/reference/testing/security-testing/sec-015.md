# SEC-015 — `courier_office_name` trusted the client despite a comment claiming otherwise

### SEC-015 — A public property documented as "never customer input" was still customer input

**Severity:** Low (a `QueryException` surfaced through checkout's own
domain-refusal handling rather than a raw 500, plus a minor data-integrity
gap; no charge, no data disclosure) · **Type:** Improper trust of
client-controlled input reaching a database write (OWASP A04 Insecure
Design — the design assumed a form's own UI is the only way to reach a
property) · **Status:** **Fixed** 2026-09-13 — confirmed by live
exploitation, then closed

**Finding.** `CheckoutPage::$courier_office_name` is `public string`, so it
is reachable via `$set()` regardless of what the rendered form does with it
— the same fact SEC-014 established for seven numeric properties, applied
here to a string one. The property carried **no validation rule** (the
`rules()` array had `courier_office_code` with `max:50` but nothing for the
name — the code's own comment said "it is never customer input").
`addressPayload()` wrote `$this->courier_office_name` **raw** into the
order-address payload, which `CreateOrder` persists to
`order_addresses.courier_office_name varchar(150)`. `placeOrder()`
validated that the *code* resolves against `offices()` but did not
re-derive the *name* from the resolved office — it trusted the property.

**Reason.** The comment "it is never customer input" was true of how the
*UI* drives the property (`selectOffice()` sets both fields together, from
an office `offices()` itself returned) but false of what the *endpoint*
accepts: a `public string` property is customer input the moment a request
can `$set()` it, independent of whether any rendered control targets it.
The class's own top-of-file docblock made the same claim more explicitly —
"`placeOrder()` re-resolves both [code and name] against that same list
before trusting either" — but the implementation only ever re-resolved the
code.

**Reproduction (confirmed live).** Office delivery, a real, resolvable
`courier_office_code` (`'OFF1'` against the test double, a real Econt/Speedy
office code in the deployed app), paired with
`$set('courier_office_name', str_repeat('x', 200))`, then `placeOrder()`:

```
SQLSTATE[22001]: String data, right truncated: 1406 Data too long for
column 'courier_office_name' at row 1
```

This did **not** surface as a raw 500 — `QueryException` extends
`RuntimeException`, which `placeOrder()`'s own
`catch (InvalidArgumentException|RuntimeException $e)` block already
handles as a domain refusal, so the customer instead saw a *plausible but
wrong* validation-style error ("Component has errors: email" in the test
harness; the real form shows whatever message that catch attaches) while
the order silently failed to place — a worse failure mode than a crash,
since it reads as an ordinary validation problem rather than a bug,
confirmed by reverting the fix and observing exactly this in the permanent
regression test.

A second, quieter case needs no overflow at all: any `courier_office_name`
under 150 characters submitted independently of a *valid* matching
`courier_office_code` reaches the database unchanged — a client can pair a
real, resolvable office code with an arbitrary, misleading name. The code
is the field a courier's own systems key off; the name is what a human
(warehouse staff, the customer's own confirmation email) reads. Nothing
before this fix kept the two consistent.

**Fix.** In `placeOrder()`, once `$validated['courier_office_code']`
resolves to a real `$office` from `offices()`, `$this->courier_office_name`
is reassigned from `$office->name` — the resolved office, not the client's
copy — before `addressPayload()` reads it. One line, closing the overflow
and the integrity gap together, and making the class's own docblock true
rather than aspirational. The stale "never customer input" comment on the
`rules()` entry and the docblock's "re-resolves both" claim were corrected
to describe what the code now actually does, rather than left to describe
a property immune to `$set()` that never existed.

Regression test:
`tests/Feature/Payment/CheckoutTest.php`, `'re-derives courier_office_name
from the resolved office rather than trusting the client value'` — sets an
oversized, mismatched name alongside a real, valid code, asserts the order
places successfully and the persisted `order_addresses.courier_office_name`
equals the *resolved* office's name, not the client's. Verified red without
the fix (the `QueryException`-as-domain-refusal failure mode above,
reproduced exactly), green with it.

**Logic for future pentests.** A comment asserting "never customer input"
on a `public` property is a claim about the *UI*, not the *endpoint* —
Livewire's `$set()` reaches any public property regardless of what any
rendered control does. The tell here was a written claim ("re-resolves
both") that did not match the implementation (resolved only one of the
two) — a docblock's description of a security property is a hypothesis to
verify against the actual code, not a substitute for reading it. Grep
target: any `public string`/`public ?int` property written into a payload
or query without appearing in the component's own `rules()`, cross-checked
against whether a sibling field it is meant to travel with is independently
re-validated — a pair where only one half is re-derived server-side is
exactly this shape.
