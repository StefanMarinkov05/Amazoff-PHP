# SEC-016 — a garbage-shaped return quantity silently became "return 1"

Part of the [security-testing index](../security-testing.md). See
[method-and-summary.md](method-and-summary.md) for how this pass was run.

### SEC-016 — `RequestReturn::$quantities`: a nested array cast to `1`, not refused

**Severity:** Low (a silently wrong answer, not a security bypass — the
quantity ceiling and ownership checks downstream still hold; no data
disclosure, no ability to return more than owned) · **Type:** Improper
input validation, adjacent to CWE-704 (Incorrect Type Conversion) · **Status:**
**Fixed** 2026-09-13 — confirmed by live exploitation, then closed

**Finding.** `RequestReturn::$quantities` is documented `@var array<int, int>`
("order_item_id => quantity") but is a plain untyped `public array`
property — Livewire hydrates whatever the client sends onto it, so a value
can arrive as a nested array rather than a scalar. `submit()` cast each
value with a blind `(int) $quantity` before checking it was actually
numeric. PHP's `(int)` cast of **any non-empty array is always `1`**,
regardless of the array's contents or depth — so a garbage-shaped value
(`quantities[42] = [['nested' => 'garbage']]`) did not fail to parse; it
silently became "return 1 unit of item 42," a legitimate-looking request
the customer never actually made.

This is the same failure class `docs/how-to/test-for-input-crashes.md`
already documents for `ProductList::$attributeValueIds` — "the playbook
would not have caught it, and neither did a test that only asserts
`assertOk()`" — found here during Sweep C's authenticated-account-page pass
(this project's own security-review handoff scoping), not by the numeric
hydration-crash playbook, since `$quantities` being an untyped `array`
never crashes at hydration regardless of what it holds.

**Reason.** The `@var array<int, int>` PHPDoc describes the *intended*
shape, not a runtime guarantee — nothing enforces it, and Larastan trusted
the annotation over the actual code path (`treatPhpDocTypesAsCertain`),
which is exactly the gap: a docblock's claim about a security-relevant type
is a hypothesis to verify, not a substitute for checking what Livewire
hydration can actually produce. `is_numeric()` on the raw value, before any
cast, is what distinguishes "a real quantity" from "whatever shape arrived."

**Reproduction (confirmed live).** A signed-in customer with a delivered,
in-window order:

```php
Livewire::actingAs($user)
    ->test(RequestReturn::class, ['order' => $order->id])
    ->set("quantities.{$line->id}", [['nested' => 'garbage']])
    ->set('reason', 'garbage nested array test')
    ->call('submit');
```

Before the fix: no error, `OrderReturn::where('order_id', $order->id)
->count()` was `1`, and the stored `return_items.quantity` for that line
was `1` — confirmed by inspecting the persisted row directly, not inferred
from the absence of an error.

**What this is not.** `$orderItemId` (the array *key*) was never
attacker-shaped by this path — only the *value* was — and
`App\Actions\Returns\RequestReturn::handle()` still re-validates every line
against the locked order's own items (`ReturnNotAllowedException::
lineNotOnOrder()` for a foreign id) and the remaining returnable quantity
(`::quantityExceedsRemaining()`) regardless of what reaches it. Since a
non-empty array always casts to exactly `1`, never higher, there was no
path to inflate a return past what the Action's own ceiling already
allows — confirmed directly: `(int)` of a one-element array, a
three-element array, and a deeply nested array all produced `1`, never
more. The bug is confined to "a garbage value is silently accepted as a
plausible one," not "a garbage value grants anything extra."

**Fix.** `submit()` now checks `is_numeric($quantity)` before casting, and
adds a form error (`quantities`, "One of the quantities entered is not a
valid number.") rather than proceeding on a value that was never actually a
number. The property's PHPDoc was corrected from `array<int, int>` to
`array<int, mixed>` with a note explaining why — a false type annotation
that Larastan would otherwise treat as certain is worse than no annotation,
since it hides exactly the gap this bug lived in.

Regression test:
`tests/Feature/Livewire/Account/RequestReturnTest.php`, `'does not silently
treat a garbage-shaped quantity as "return 1"'` — asserts the component
raises a `quantities` error and that zero `OrderReturn` rows are created.
Verified red without the fix (no error, one return silently created with
quantity `1`), green with it.

**Logic for future pentests.** `(int)` of any non-empty PHP array is always
`1` — not the array's length, not its first element, always exactly `1`,
regardless of nesting or contents. This is the mechanism, not incidental to
this one property: any `foreach ($clientArray as $k => $v) { $v = (int)
$v; ... }` pattern on a Livewire-hydrated array property is vulnerable to
the same silent coercion the moment a value can arrive as an array instead
of a scalar, and — unlike the numeric-hydration-crash class (SEC-014) — it
produces **no crash and no validation error**, only a wrong answer that
reads as a correct one. Grep target: every `(int)`/`(float)` cast inside a
loop over a `public array` Livewire property, cross-checked for an
`is_numeric()` (or equivalent) guard *before* the cast, not only after.
