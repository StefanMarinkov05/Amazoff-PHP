# SEC-017 — six plain-lookup admin resources had no column-length guard at all

Part of the [security-testing index](../security-testing.md). See
[method-and-summary.md](method-and-summary.md) for how this pass was run.

### SEC-017 — Six Filament resources crashed on the first oversized field, found by the content_editor role-scoped scan

**Severity:** Low (unhandled crash under a staff-authenticated session only;
no data disclosure past what an Ignition trace already leaks under local
`APP_DEBUG=true`, no privilege escalation, no cross-tenant impact — every
affected resource is a global lookup table, not per-customer data) ·
**Type:** Improper input validation, CWE-1284 (Improper Validation of
Specified Quantity in Input) · **Status:** **Fixed** 2026-09-13 — confirmed
by live exploitation for all six, then closed

**Finding.** Every `TextInput` on six plain-lookup Filament resources'
create forms — `ArticleCategoryForm`, `TagForm`, `AttributeForm`,
`BrandForm`, `ProductCategoryForm`, `AttributeValueForm` — carried **no
`->maxLength()` call at all**. Filament derives both its client-side
`maxlength` HTML attribute and its server-side validation rule from that
one method; without it, nothing in the stack stops a value longer than the
underlying migration's column from reaching an `INSERT` raw. Every one of
the six resources is exactly the "plain lookup table, default Filament
CRUD" category `docs/reference/coding-conventions.md` and ADR-0007 name
explicitly (`Brand`, `Tag`, `Attribute`, `AttributeValue`,
`ProductCategory`, `ArticleCategory`) — no Action sits in front of the
save to catch this, by design, since wrapping a single-table save in an
Action for these resources was a deliberate non-goal.

Found by the content_editor role-scoped OWASP ZAP scan (this project's own
security-review handoff's Sweep 4), which submitted an oversized `name` to
`/admin/article-categories/create` and got back an uncaught 500 —
`POST /livewire/update` returning a full stack trace, confirmed in the
webserver access log and the application's own `laravel.log`. The scan
itself did not classify this as a security alert (ZAP has no built-in rule
for "this form crashed the server"), so it would have been missed by
reading only the alert summary; it surfaced only because the raw access
log was checked directly for anomalous status codes while confirming the
`/admin/logout` exclusion held (SEC-014's fix), which is the reason to read
scan logs rather than only scan reports.

**Reason.** These six resources are exempt from the Action layer *by
design* (ADR-0007) precisely because a single-table save with no
cross-table invariant "buys nothing" from an Action wrapper. That reasoning
is correct about invariants, but it does not extend to a bounds check a
plain migration column already implies — nothing about "no Action needed"
implies "no `->maxLength()` needed," and every one of these six forms
conflated the two. Filament's default `TextInput` imposes no length limit
of its own; the limit has to be stated explicitly, once per field, matching
the column it writes to.

**Reproduction (confirmed live for all six, via `Livewire::test()->fillForm()->call('create')`
— not assumed from the missing method call alone):**

| Resource | Field | Column | Overflow value | Result before fix |
|---|---|---|---|---|
| `ArticleCategory` | `name` | `varchar(50)` | 60 chars | `QueryException: Data too long for column 'name'` |
| `Tag` | `name` | `varchar(30)` | 40 chars | Same shape |
| `Attribute` | `name` | `varchar(50)` | 60 chars | Same shape |
| `Brand` | `name` | `varchar(50)` | 60 chars | Same shape |
| `ProductCategory` | `name` | `varchar(50)` | 60 chars | Same shape |
| `AttributeValue` | `value` | `varchar(100)` | 110 chars | Same shape |
| `AttributeValue` | `color_hex` | `char(7)` | 8 chars | Same shape |

Every one is an uncaught `PDOException`/`QueryException` propagating
through `Filament\Resources\Pages\CreateRecord::handleRecordCreation()`,
confirmed via `storage/logs/laravel.log`'s full stack trace — an Ignition
debug page to the signed-in staff member under local `APP_DEBUG=true`; a
bare 500 with debug off, but still an unhandled crash on ordinary
form-filling rather than an attack, since nothing about typing a long
category name looks adversarial from the person doing it.

**What this is not.** Every affected resource requires `canAccessPanel()`
plus the specific `create_*` permission (confirmed against
`docs/reference/permissions.md`'s role matrix — only `administrator` and,
for `ArticleCategory`/`Tag`, `content_editor` can reach these forms at
all), so this is not reachable by an unauthenticated visitor or a customer
account. It is a crash on a form a legitimate staff member could trigger by
accident (pasting a long name, a copy-paste including trailing whitespace
that pushes past the limit), not a privilege or data-disclosure bug.

**Fix.** `->maxLength(N)` added to every affected field, `N` taken directly
from the corresponding migration's column definition (`->string('x', N)`/
`->char('x', N)`) rather than an arbitrary round number, so the form's own
limit and the schema's limit cannot drift apart:

- `ArticleCategoryForm`: `name` → 50, `slug` → 100, `description` → 255.
- `TagForm`: `name` → 30, `slug` → 60.
- `AttributeForm`: `name` → 50, `slug` → 60.
- `BrandForm`: `name` → 50, `slug` → 100.
- `ProductCategoryForm`: `name` → 50, `slug` → 100, `description` → 255.
- `AttributeValueForm`: `value` → 100, `slug` → 120, `color_hex` → 7.

`RoleForm` and `ContactMessageForm` — the only other two Filament forms
with zero `->maxLength()` calls anywhere — were checked and are correctly
exempt: every `TextInput` on both is `->disabled()->dehydrated(false)`
(read-only display of data written elsewhere), and `ContactMessageForm`'s
one genuinely writable text field (`internal_note`) is a `Textarea` over a
`text` column with no realistic bound to enforce.

Regression tests: `tests/Feature/Filament/PlainLookupMaxLengthTest.php`,
one case per field above, each asserting `assertHasFormErrors()` and that
no row was created — verified red without the fix (the exact
`QueryException` reproduced for all seven cases), green with it.

**Logic for future pentests.** "This resource needs no Action" (ADR-0007's
own reasoning) and "this resource needs no length validation" are
independent claims a design note can accidentally bundle together — the
first is about business invariants an Action would enforce; the second is
about a database column's own hard limit, which exists regardless of
whether an Action sits in front of it. Grep target for the next resource:
every `TextInput::make(...)` with no `->maxLength()` in its chain,
cross-checked against the model's migration for the column it writes to —
a `Textarea` over a `text`/`longText` column is the one legitimate
exemption, since those have no realistic bound worth enforcing. This class
is easy to miss from an alert-summary-only scan read: ZAP has no rule that
says "this crashed the server," so the raw access/application log has to
be checked directly for anomalous 500s during any authenticated crawl, not
inferred from the alert list alone.
