# ADR-0003: Seeding the database

Status: Accepted
Date: 2026-08-10 · Deciders: Stefan Marinkov

## Context

The specification's preamble makes seeders mandatory: the application has to
come up populated with sample data and be easy to start locally. §37 adds a
second requirement that seeded data has to satisfy — criteria 2, 3, and 5 are
about browsing, filtering, and cart validation, none of which can be
demonstrated against an empty or uniform catalogue.

Three situations need data, and they want different data:

- **Tests and CI.** Runs on every commit. Wants the smallest fixture that
  exercises the code, and wants it fast.
- **The deployed demo.** Read by people. Wants a catalogue that looks like a
  real shop, in the low hundreds of products.
- **Stress testing.** Wants row counts high enough that missing indexes and
  N+1 queries become visible. Nobody reads the individual rows.

Treating these as one dataset makes each of them worse: the test suite pays for
demo volume, and the demo carries rows nobody wrote.

## Decision

### Three seeders, not one

`DatabaseSeeder` stays small and deterministic — roles, staff accounts, a
handful of products covering the branches the tests need. This is what CI runs.

`DemoSeeder` loads the committed demo fixtures and is not part of the merge
gate. `StressSeeder` generates volume programmatically. Neither runs in CI.

Production runs `DatabaseSeeder` for reference data that the application needs
in order to work at all — roles, carriers, VAT rates. Catalogue content in
production is entered through the admin panel, never seeded.

### Demo data is committed JSON fixtures, authored once

Prose — product names, descriptions, SEO fields, article bodies — is generated
by an LLM in batches, reviewed, and committed. Numbers, states, and
relationships are generated by rules rather than by the model, because what the
demo has to show is not 500 plausible products but a catalogue that covers
every branch of the UI: out of stock, one left, discount active, discount
expired, 1 variation, 5 variations, inactive, no image, a name long enough
to break a card layout.

Content diversity is what an LLM provides. State diversity is what §37 is
graded on, and rules provide it more reliably.

### Fixtures are nested documents with natural keys, not table dumps

One JSON document per aggregate root — a product carries its variations,
images, specifications, and stock inside it. Cross-aggregate references use
slugs (`"category": "power-tools"`), never integer IDs; the seeder resolves
slugs against a lookup map built once per table.

The fixture therefore contains no foreign keys at all. Referential correctness
becomes a property of the seeder, which is tested once, rather than a property
of whatever generated the file.

### A validator runs before the seeder, not inside it

`fixtures:validate` checks three layers: document shape; column constraints
derived from the schema and from `App\Enums` rather than restated; and
cross-document invariants the database cannot express — slug resolvability, SKU
uniqueness across products and variations, `discount_price < regular_price`,
every product having at least 1 variation.

It exits non-zero and reports every failure with a full path. The point is not
that the database would miss these — it would catch most of them — but that it
catches them one at a time, mid-transaction, after thousands of rows are
already written.

### Transactional data is produced by running Actions

Orders, reservations, status history, coupon redemptions, and payments are not
fixtures. They are created by calling the same Actions the storefront calls.

This keeps totals, inventory movements, and status history consistent by
construction, exercises the code §37 criterion 20 requires tested, and makes it
impossible to seed an order state the state machine cannot actually reach.
Hand-written order fixtures would bypass `TransitionOrderStatus`, which is
forbidden everywhere else in the codebase.

It also supplies the stress volume: 50,000 orders across 500 products is a
loop, and it produces the skewed distribution — a few hot products, a long
dead tail — that makes an index problem visible. Uniformly random orders hide
it.

### Seeding is deterministic

Faker is seeded from a fixed value, and lookup arrays are sorted explicitly
before being indexed into. `migrate:fresh --seed` produces the same database
every run, so screenshots stay valid and a bug found yesterday reproduces
today.

### Courier reference data comes from the courier APIs

Cities, postcodes, and office identifiers are fetched from Econt and Speedy and
committed as fixtures. Generated ones would be rejected by the real API, and
§37 criterion 13 requires at least one courier working against a real test
environment.

### Product images are generated, not collected

Placeholder images are rendered at seed time into `storage/` from the category
and product name. No image binaries enter git.

## Consequences

+ CI runs against a small fixture and stays fast; the demo can be as large as
  it needs to be.
+ The committed fixtures make `migrate:fresh --seed` an offline, deterministic
  operation with no API calls at deploy time.
+ Demo orders exercise the real order pipeline, so seeding doubles as an
  integration check.

− An LLM-authored fixture is deterministic once committed but not
  regenerable — re-running produces different text. The committed file becomes
  the source of truth permanently, and later corrections are hand edits. This
  is why the schema and the validator have to be settled before the content is
  generated.
− Three seeders is more to maintain than one, and the demo fixtures can drift
  out of step with the schema. The validator is what catches that, so it has to
  run in CI even though `DemoSeeder` does not.
− Generated placeholder images make the demo look unfinished next to a real
  shop. Accepted: the alternative puts someone else's copyrighted photographs
  on a public URL.
− None of this is built. The seeders, the fixture format, and the validator do
  not exist yet.

## Alternatives rejected

- **Scraping a real shop.** Gives genuine prose and photographs, at the cost of
  republishing another company's copy and images on a public deployment, and
  several hundred megabytes of binaries in git. It also supplies content
  realism, which nothing in §37 measures.
- **CSV fixtures.** A product is an object graph — variations, attribute
  values, images, specifications, per-variation stock. Flattening that into rows
  is what makes an import parser fragile. JSON nests for free and fails at parse
  rather than producing a plausible wrong row.
- **One JSON file per table, with integer foreign keys.** Requires whatever
  authored it to keep IDs consistent across a dozen files. An error produces an
  orphaned or cross-wired row that inserts successfully and is found much later.
- **Generating stress volume with an LLM.** Cost scales with row count, and the
  output homogenizes past a few hundred records — the most expensive way to buy
  the least diversity.
- **Faker at seed time for the demo.** Fast and always in sync with the schema,
  but `fake()->words(3)` reads as noise on a product page, which defeats the
  purpose of a demo.
- **One seeder for all three situations.** Every test run pays for demo volume.
